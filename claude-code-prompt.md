# Промпт для Claude Code

Как пользоваться:
1. Положите `open.zip` распакованным в папку проекта, чтобы получилось `forte-guard/data/open/videos/*.mov` и `forte-guard/data/open/open_labels.xlsx`.
2. Положите рядом файл [violation-types-draft.md](../analysis/violation-types-draft.md) как `forte-guard/docs/violation-types-draft.md`.
3. Откройте Claude Code в папке `forte-guard` и вставьте весь текст ниже, между линиями.

---

Ты дорабатываешь проект для датахона ForteBank 2026. Работай в текущей папке. Проект уже запускается через `docker compose up --build` и проходит `scripts/jury_check.py`. Сначала прочитай README.md, `backend/app/*`, `docs/violation-types-draft.md` и этот промпт целиком. Потом составь план и работай по нему без лишних вопросов. Останавливайся и спрашивай меня только в случаях из раздела «Когда спрашивать».

## Задача кейса

Локальный веб-сервис получает видео .mov с камеры над кассой банка (обзор сверху и под углом, одна касса, кассир, клиенты, инкассаторы, без звука). Он определяет возможные нарушения кассовой дисциплины. Для каждого нарушения нужны тип, таймкод, 1–3 кадра-доказательства, описание того, что видно и почему это нарушение, и ссылка на норму (документ и пункт).

Оценка (100 баллов, жюри проверяет автоматически через API):
- 25: верный вердикт по видео;
- 15: точность таймкода и релевантный кадр;
- 15: верный тип нарушения;
- 15: верная норма без выдуманных ссылок;
- 10: устойчивость к новым видео и **другому ракурсу камеры** (финальное тестовое видео снято с другого угла);
- 10: готовность продукта (UI, надёжная загрузка);
- 10: архитектура и локальность.

Пропуск нарушения недопустим, ложных срабатываний должно быть минимум, то есть приоритет на полноту (recall). В тесте могут быть типы нарушений, которых нет в обучающих данных.

## Жёсткие ограничения (нарушение = дисквалификация или штраф)

1. **Никаких облачных ИИ и API.** Ни одного запроса во внешние сервисы распознавания, LLM или vision, даже с кадрами или текстом. Всё работает локально.
2. **Офлайн.** Веса моделей скачиваются на этапе `docker build` и лежат в образе. Во время работы интернета нет.
3. **Только модели и библиотеки с лицензией для коммерческого использования**: Apache-2.0, MIT, BSD. **Не используй Ultralytics YOLOv5/v8/v11 (AGPL-3.0).** Подходят, например, RT-DETR через Hugging Face transformers (Apache-2.0), YOLOX (Apache-2.0), MediaPipe (Apache-2.0), OpenCV. Лицензию каждой модели и её весов впиши в `docs/LICENSES.md`.
4. **Никакого распознавания и идентификации лиц.** Детекция человека как объекта разрешена, лиц нет.
5. **Не утверждай то, чего не видно на видео**, например правильность записей в журнале.
6. **Лимит 5 минут на видео.** Самое длинное видео в данных 145 с. Сервис работает на CPU ноутбука без GPU (4–8 ядер). Цель: ≤ 2 минуты на 145-секундное видео. Анализируй 2–5 кадров в секунду, уменьшай разрешение.
7. **Формат ответа жюри менять нельзя.** `backend/app/schemas.py` трогать нельзя, кроме исправления ошибок. Поскольку отдельного поля для нормы в ответе нет, ссылку на норму добавляй в конец `description` в виде «Норма: <документ>, <пункт>».

## Данные

`data/open/videos/`: 42 клипа, 22 с нарушением и 20 без. Имена смешанные: `X-1.mov` и `#U0425-N.mov` (это кириллическая «Х»). В `data/open/open_labels.xlsx` колонки «имя файла | таймстемп ("22 секунда", "1минута 8 секунда") | нарушение / без нарушения». Тип нарушения не указан. X-4 и X-47 это побайтово один файл с разными таймстемпами (57 с и 68 с). X-5 и X-48 тоже совпадают. Съёмка ведётся минимум в 3–4 разных комнатах и ракурсах, поэтому правила **привязывай к объектам** (люди, стол, сейф, дверь, сумка), а не к пиксельным координатам.

Черновик типов по стоп-кадрам лежит в `docs/violation-types-draft.md`. Это гипотезы. Видео, помеченные «уточнить», смотри по кадрам внимательнее сам. Окончательные типы подтвердит человек.

## Что сделать (по порядку)

1. **Ревизия данных.** Скрипт `ml/inspect.py` нарезает кадры вокруг каждого таймстемпа. Изучи все 22 нарушения и 20 чистых клипов и уточни таблицу «видео → тип → что видно» в `docs/violation-types.md`. Чистые клипы нужны, чтобы понять, что нормой не является.
2. **Таксономия.** Сделай 5–9 типов с кодами (например `CASH_UNATTENDED`, `UNAUTHORIZED_PERSON`, `SAFE_OPEN`, `PERSONAL_ITEMS`, `FOOD_DRINK`, `COUNT_PROCEDURE`, `CIT_PROCEDURE`, `WORKPLACE_LEFT`). Для каждого задай описание и признаки на видео. Добавь общий тип «Подозрительное действие с ценностями» для неизвестных случаев, чтобы не пропускать нарушения.
3. **Нормы.** Создай `docs/legal-sources.md` и `backend/app/seed/legal_rules.json`. Ищи только публичные акты РК: постановления НБРК о кассовых операциях, инкассации, организации кассовых помещений и мерах безопасности, сайт adilet.zan.kz. **Если не уверен в номере пункта, пиши только название документа и ставь `"verified": false`.** Ничего не выдумывай: за выдуманные ссылки штраф. Если в окружении нет интернета, оставь заготовки с `verified: false` и перечисли в отчёте, что мне нужно найти.
4. **ML-пайплайн** в `backend/app/ml/`, сменная замена заглушки в `analyzer.py`:
   - декодирование с шагом 2–5 fps (OpenCV);
   - детектор объектов с коммерческой лицензией (person, handbag, backpack, cup, bottle, cell phone, laptop и т. п.) и простой трекер (IoU или ByteTrack-подобный, лицензия MIT/Apache);
   - автоматический поиск сцены на первых кадрах: стол (крупная горизонтальная поверхность или зона, где кассир сидит дольше всего), сейф, дверь. Без ручной разметки, чтобы работало на новом ракурсе. Ручную калибровку зон оставь как необязательную настройку;
   - детекция «ценностей на столе»: деньги и инкассаторская сумка. В COCO таких классов нет, поэтому используй цвет и текстуру в зоне стола, разницу с фоном и появление новых предметов. Если без этого не обойтись, дообучи лёгкий классификатор на кадрах из обучающих видео;
   - состояние сейфа (открыт или закрыт) по изменению его области;
   - правила по типам с порогами в `backend/app/ml/rules.yaml`: например, ценности на столе и в кадре нет кассира дольше N секунд; больше двух человек в кассовой зоне; сейф открыт, а кассир не рядом;
   - таймкод равен началу события, кадры берутся на 0, +1 и +2 с от него;
   - описания на русском, конкретно и без домыслов, с нормой в конце.
5. **Оценка качества.** Скрипт `ml/eval.py` прогоняет все 42 видео и печатает таблицу: вердикт (TP/FP/FN/TN), ошибку таймкода в секундах, тип и время обработки. Итог: recall, precision, средняя ошибка таймкода, максимальное время. Сохраняй результат в `docs/eval-latest.md`. Цель: recall = 100 %, precision ≥ 80 %, ошибка таймкода ≤ 3 с. Подбирай пороги, но не подгоняй под конкретные имена файлов.
6. **Устойчивость к ракурсу.** Проверь на аугментированных копиях: поворот ±15°, перспективное искажение, масштаб 0.7–1.3, зеркало, яркость. Добавь режим `ml/eval.py --augment`.
7. **Журнал и кассиры.** Сделай сид-скрипт `backend/app/seed/` с демо-кассами, сотрудниками и сменами (вымышленные имена), а также с типами и нормами. Нарушение должно автоматически получать кассира по смене (`tasks.find_teller` уже есть). Миграции схемы делай через Alembic.
8. **UI** (`frontend/`): прогресс обработки, таймлайн с метками нарушений над плеером, норма отдельной строкой в карточке, фильтры журнала по дате, типу и статусу, экспорт журнала в CSV. Сайт должен работать с телефона. Фирменный стиль менять пока не надо.
9. **Безопасность:**
   - rate limit на `/api/v1/analyze` по ключу и IP через Redis;
   - проверка контейнера через ffprobe (уже есть);
   - лимиты памяти и CPU для worker в compose;
   - заголовки безопасности (CSP, X-Content-Type-Options);
   - CORS только для своего origin;
   - ошибки без стектрейсов наружу;
   - секреты только из `.env`;
   - `pip-audit` в CI.
10. **Тесты и CI:** pytest на правила (синтетические события), контрактный тест схемы ответа, `jury_check.py` в GitHub Actions на 2–3 коротких клипах (видео в репозиторий не коммить, используй синтетическое видео для CI).
11. **Документация** (входит в сдачу кейса): README (установка, запуск, API, ключ), `docs/architecture.md` со схемой, `docs/violation-types.md`, `docs/legal-sources.md`, `docs/limitations.md` (известные ограничения и ошибки), `docs/LICENSES.md`.

## Как работать

- Иди маленькими шагами. После каждого шага запускай `jury_check.py` и `ml/eval.py`, а также `docker compose up --build`, если менял зависимости.
- Используй git: отдельный коммит на каждый шаг с понятным сообщением. `data/` и `.env` не коммить.
- После этапов 5 и 6 покажи мне таблицу метрик.
- Если сборка Docker стала заметно дольше, объясни почему. Ставь только CPU-версии библиотек, например `torch` с `--index-url https://download.pytorch.org/whl/cpu`.

## Когда спрашивать меня

- Тип нарушения на видео неочевиден, и от решения зависит таксономия.
- Норма найдена, но ты не уверен, что она подходит.
- Нужно поставить модель или библиотеку, лицензию которой ты не можешь подтвердить.
- Метрики не выходят на цель после разумных попыток: покажи, на каких видео ошибки.

В конце дай короткий отчёт: что сделано, метрики, что осталось, и список ручных задач для меня.
